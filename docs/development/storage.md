# SQLite, files and compatibility

The installed desktop app and CLI use the same Rust store. The default root is `<installation>/data`; the CLI also accepts an explicit absolute data directory. A cross-process operation lock beside the vault survives replacement of the active vault. Read-only CLI discovery and queries may open a legacy database but must not create directories, add tables or change the database. A new empty library has a defined discovery response.

| Stored state | Contract |
| --- | --- |
| `vault/folio.sqlite3` | Use snake_case SQL identifiers, bound query parameters, and camelCase JSON field names for serialized bodies. Writable connections enable foreign keys, DELETE journaling, FULL synchronization and a busy timeout. |
| `records(id, body, deleted)` | The ID remains stable across edits. `updatedAt` is the record revision. Validate expected revisions as part of the write and advance managed timestamps monotonically. Preserve field IDs and order on targeted edits. |
| `attachments(id, record_id, body, deleted)` | A foreign key and the `attachment_record` index connect files to records. Keep the stable ID and revision checks on rename, replacement and removal. The manifest stores a vault-relative path. Resolve it under the managed vault before use. |
| `category_catalog(id, body)` | One row with ID 1 stores ordered definitions and a catalog revision. Missing definitions on an older library resolve to the built-in catalog on read. Use stable category IDs for associations and managed file prefixes. |
| Soft deletion | For records, 0 is active and 1 is deleted. For attachments, 0 is active, 1 is individually removed, and 2 is hidden with its parent. Undoing a record deletion restores only its attachments marked 2. |

Maintain existing ordering and machine-readable output. Active records in the backend snapshot are sorted by modification time descending and attachments retain their stored order. Resolve only the files an operation needs. Keep source files intact on import. New managed filenames use a single underscore between collection ID and suffix, retain a safe extension and reject collisions. Existing names remain valid, including names generated by earlier releases. Renaming a category changes its display label without moving files.

## Changes and recovery

1. Identify which contract changes: database schema, persisted JSON, CLI schema, or ZIP manifest. They evolve independently. Document the old and new shapes, fixtures, readers and recovery before changing a format.
2. Keep a migration in the writable initialization path. Use a transaction for related SQL changes, validate relationships before commit and make interrupted operations recoverable. For changes spanning files and SQL, stage the file, preserve the previous bytes, and clean up or restore on failure. Take the operation lock across the whole logical change.
3. Read an old synthetic library through the CLI, check that read-only access leaves the database unmodified, upgrade and reopen through the writable path, and verify both entry points. Cover stale revisions, failed or interrupted writes, single-attachment and parent undo, missing files and stable paths/hashes.
4. Current backup exports use v1 for an exact default catalog and v2 for a customized catalog. Restore supports both, validates the archive and relationships, and retains the previous active vault. Test default and customized round trips, invalid archives and restore failure without replacing good data.
